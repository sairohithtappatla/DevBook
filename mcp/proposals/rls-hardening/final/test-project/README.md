# Loading the DevBook baseline into the (empty) InsForge TEST project

Why: the preflight found `devbook-rls-test` (393cz2pc, PostgreSQL 15.18) completely empty: no tables, enums, triggers, policies or bucket. 01-04 modify existing objects, so the application schema has to exist first.

`00_baseline_schema.sql` = the schema as production has it today (before any hardening), derived from `../sandbox/schema.sql` by `make-baseline.mjs`. **Exact** parts come from your 2026-10-18 production export (`books, phases, steps, book_members, attachments, users`, all functions, triggers, indexes, policies). **Reconstructed** (parity gap): the columns of `book_access, user_followers, step_progress, book_progress, book_revisions` and the enum values of `book_difficulty`/`step_type`. For RLS testing that is enough; for exact parity compare it with a read-only production export (below).

Validated locally (`validate-loader.mjs`, PostgreSQL 15.18 with an InsForge-like platform: roles, auth.users columns, `auth.uid()` from `request.jwt.claims`, default privileges arwd, no CREATE on public): the file loads, creates 11 tables / 24 policies / 5 enums / 7 triggers, reproduces the draft leak, 01-04 apply on top, the scenario passes, rollbacks restore the loaded baseline. Not validated: loading through InsForge's own import path (see below).

## Steps (TEST folder only, after `guard.mjs` printed GUARD OK)
1. Load: `npx @insforge/cli db import mcp/proposals/rls-hardening/final/test-project/00_baseline_schema.sql` (the CLI reads a local file and posts it; whether it executes DO blocks, `$function$` bodies and BEGIN/COMMIT correctly is unverified). Fallback: run the file in chunks through the InsForge MCP raw-SQL tool, in file order. If an object already exists, stop and report; do not DROP anything.
2. Create the storage bucket `book-assets` as PRIVATE through the MCP/CLI (`npx @insforge/cli storage create-bucket book-assets --private`); no real files.
3. Verify the load: 11 tables, 24 policies, 5 enums, 7 triggers, RLS enabled everywhere; `trigger_audit_metadata` sets `steps.updated_at = now()` on update.
4. Optional parity check against production (READ-ONLY, run by YOU in the PRODUCTION folder, output stays on your disk, never pasted): `npx @insforge/cli db export --no-data --include-functions --include-views --include-sequences -o prod_schema.sql` and save it as `D:\Project\devbook-test\evidence\prod_schema.sql` (not committed). Then Antigravity may diff the five reconstructed tables, the enum values and the columns of the others against what was loaded and list every difference. Production's `db policies/triggers/indexes --json` are the same read-only kind of command if more detail is needed.
5. Re-run the catalog snapshot as the new "before".
6. Seed the synthetic fixture: create the five users `owner|editor|reviewer|viewer|stranger@example.invalid` through the API sign-up (passwords chosen by you, kept out of chat and out of the repo), set `email_verified = true` for them in `auth.users` on the TEST project, then run `10_seed_fixture.sql` (it resolves the users by e-mail, refuses to run twice, creates 5 books incl. a soft-deleted one with non-owner members, attachment ROWS only, no files). Validated locally: after 01-03 `reader_book_tree` matches the hand-written expectations of `../../rpc-expectations.mjs` for all 6 actors x 5 books x 2 modes (60 combinations). Remove it with `10_seed_rollback.sql`.
7. Continue with Phase 5 of HANDOFF.md (baseline reproduction BEFORE applying 01-04): the fixture must show the known defects at this point.
